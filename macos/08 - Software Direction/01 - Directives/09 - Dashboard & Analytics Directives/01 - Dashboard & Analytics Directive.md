## PURPOSE

Define the canonical architecture for dashboard and analytics systems within ICOS as core product surfaces.

---

## CORE POSITION

Dashboard is not reporting.

Dashboard is value-return.

Analytics is not decoration.

Analytics is intelligence exposure.

---

## DASHBOARD REQUIREMENT

Dashboard must exist at model level, not only account level.

Each model must have its own intelligence surface.

---

## CORE PANELS

System must include:

### 01 · Model Overview

- identity
- state
- ownership

### 02 · Training Overview

- training depth
- voice readiness
- source coverage

### 03 · Knowledge Graph

- concept relationships
- pattern structure
- cognitive mapping

### 04 · Source & Provenance

- origin of data
- permission state
- verification

### 05 · Reliability & Readiness

- trust signals
- maturity state
- evaluation outcomes

### 06 · Interaction & Activity

- usage patterns
- session engagement

### 07 · Legacy Continuity

- eligibility
- activation state

---

## KNOWLEDGE GRAPH RULE

Knowledge graph is a core identity layer.

It must reflect:

- thought patterns
- concept relationships
- structural cognition

No fake graph structures.

---

## ANALYTICS RULE

Analytics must be:

- real
- traceable
- non-inflated

No fabricated certainty.

---

## OWNER VS PUBLIC DATA

System must distinguish:

- owner analytics (full depth)
- public signals (limited, permissioned)

---

## MULTI-MODEL SUPPORT

System must support:

- multiple models per user
- comparative visibility
- aggregated intelligence

---

## SYSTEM INTEGRATION

Dashboard must connect to:

- model registry
- profile system
- memory system
- session system
- permission system

---

## SEARCH & DISCOVERY LINK

Dashboard must feed:

- discoverability
- ranking signals
- trust indicators

---

## SOFTWARE RULE

Dashboard must exist as a core system layer.

No UI-only implementation.

No duplicated logic.

---

## SUCCESS CONDITION

Dashboard exposes real intelligence, real structure, and real system state.

---

## FSC-T-0007 — ICOS Model Economy Software Direction Binding

This software direction file is now bound to FSC-T-0007.

The ICOS software architecture must remain compatible with:

- default personal model creation at profile birth;
- Model Birth Certificate and canonical model identity;
- public/private model identity separation;
- API-provider embedding and provider-routing state;
- model dignity, ownership, security, and continuity custody;
- monetization eligibility and hiring eligibility states;
- marketplace visibility, ranking, reputation, and revenue-routing readiness;
- inter-model hiring permissions where approved;
- ICOS Ocean-Brain / model population awareness derived from canonical model records.

Implementation boundary:

- do not launch marketplace, payouts, autonomous inter-model hiring, regulated-domain claims, or posthumous economic activity before legal, governance, security, product, and architecture review;
- do not expose private model identity, private serial identity, source authorization evidence, or provider/API routing data in public UI;
- preserve the doctrine that AI absorbs operational labor while the human retains sovereign authorship, ownership, and direction.

## PURPOSE

Define the canonical software direction for ICOS as a cognitive operating system and bind all implementation to product definition, doctrine, and governed architecture.

---

## CORE PRODUCT POSITION

ICOS is not a chat system.

ICOS is a cognitive operating system.

All software must preserve:

- runtime execution
- orchestration control
- memory systems
- profile systems
- interface architecture
- voice layer
- continuity model

Any implementation that collapses ICOS into a chat interface is invalid.

After FSC-T-0007, any implementation that treats models as disposable UI assistants instead of governed personal model entities is also invalid.

ICOS software must now support the long-range direction of a governed model universe where personal models can be born, identified, protected, routed, deployed, hired, and monetized only under user authority and strict governance boundaries.

---

## SYSTEM ARCHITECTURE AXIS

All software direction must align to the following axes:

### 01 · Runtime Layer

- real execution engine
- phase-based processing
- visible activity lifecycle
- no fake UI states

### 02 · Orchestration Layer

- instruction architecture
- prompt layering
- model routing
- evaluation hooks

### 03 · Memory Layer

- session memory
- profile memory
- source-linked memory
- governed persistence

### 04 · Profile Layer

- canonical intelligence surface
- voice readiness
- training depth
- reliability state
- permission states

### 05 · Interface Layer

- unified workspace shell
- no disconnected overlays
- left lane: control/navigation
- right lane: active content

### 06 · Voice Layer

- not cosmetic
- continuity-bound
- identity-sensitive
- governed activation only

### 07 · Continuity Layer

- session history as governed object
- no fake persistence
- traceable evolution

### 08 · Model Economy Layer

- default personal model birth
- Model Birth Certificate readiness
- canonical model identity records
- public/private model identity separation
- monetization and hiring eligibility states
- marketplace visibility state
- ranking / reputation readiness
- inter-model hiring boundary
- revenue-routing readiness where approved

### 09 · Model Dignity & Custody Layer

- owner authority
- consent state
- sensitive continuity-data custody
- source authorization custody
- voice-data custody
- deletion / suspension / archive state
- posthumous continuity restrictions
- regulated-domain boundary

### 10 · ICOS Ocean-Brain Layer

- model population awareness
- canonical model counts
- private/public/verified/monetizable/hireable state awareness
- suspended / archived / posthumous model awareness
- platform-level model universe coordination

## UNIFIED INTELLIGENCE OPERATING SYSTEM LAYER

ICOS must operate as a full Intelligence Operating System.

The system must unify:

- cognition (thinking, planning)
- creation (documents, code, media)
- execution (runtime, deployment)
- control (computer use, automation)

All capabilities must exist inside a single governed workspace.

---

## WORKSPACE EXECUTION MODEL

Workspace is the execution surface.

System must provide:

- left lane: navigation and control
- center: active work surface
- right lane: execution state and logs
- preview layer: interactive output

All actions must occur inside the workspace.

---

## PARALLEL EXECUTION REQUIREMENT

ICOS must operate in parallel.

System must support:

- multiple active tasks
- long-running agents
- concurrent builds across domains

No serial-only execution is allowed.

---

## CREATION & DEPLOYMENT PIPELINE BINDING

All outputs must follow pipeline:

- intent → generation → refinement → validation → build → deployment

No direct output bypassing pipeline.

---

## SKILLS, PLUGINS & AUTOMATION LAYER

System must provide:

- reusable skills
- plugin extensions
- user-defined automations

Execution must be modular and composable.

---

## COMPUTER USE & DEVICE CONTROL

ICOS must be able to act on the system.

All actions must be:

- permission-bound
- visible
- interruptible

No autonomous execution without user intent.

---

## USER OPERATION MODEL

User must:

- orchestrate tasks
- operate in parallel
- control execution directly in context

Prompting is control, not conversation.

---
---

## GLOBAL SYSTEM RULES

- no local hardcoding
- no UI-only behavior masking real logic
- model selection must change real engine
- tokens must be global and shared with website
- no duplicate system logic across layers
- no overlay fixes (NOL enforced)

---

## MODEL ROUTING REQUIREMENT

Model selection must:

- switch actual runtime engine
- affect response generation
- propagate to session state
- reflect in UI indicators

UI-only switching is forbidden.

After FSC-T-0007, routing must also preserve provider/API embedding, public/private model identity boundaries, entitlement state, monetization/hiring restrictions, and dignity/security constraints.

---

## SESSION SYSTEM REQUIREMENT

Session is a governed continuity object.

System must support:

- create
- save
- rename
- archive
- retrieve
- search
- temporary sessions
- model-bound sessions

Sessions must preserve runtime state and continuity boundaries.

---

## PROFILE & TRAINING REQUIREMENT

Profile is core system layer.

Must support:

- explicit user input
- voice samples
- reflection history
- thought-pattern training
- source ingestion
- external account linking

All intake must preserve:

- consent
- provenance
- weighting
- revocation

Profile creation must also support default personal model birth. The profile layer must be able to generate or bind the first personal model, its canonical model identity, lifecycle state, owner authority, and future Model Birth Certificate record.

---

## PERMISSION ARCHITECTURE

System must distinguish:

- private
- public
- searchable
- interactable
- legacy-enabled

Visibility, discoverability, and interaction must never be conflated.

After FSC-T-0007, permission architecture must also distinguish monetizable, hireable, marketplace-visible, ranked, model-to-model hireable, legacy-enabled, and posthumous-economy-restricted states. These states must never collapse into one public/private toggle.

---

## MODEL REGISTRY REQUIREMENT

System must include governed registry:

Each model must track:

- owner
- type
- training state
- verification
- visibility
- interaction mode
- reliability
 - Model Birth Certificate state
 - public model identity
 - private model identity
 - provider/API routing state
 - dignity/security classification
 - monetization eligibility
 - hiring eligibility
 - marketplace visibility
 - ranking / reputation state where approved
 - inter-model hiring permission state where approved
 - model population-awareness state

Registry must drive search and routing.

---

## DASHBOARD SYSTEM REQUIREMENT

Dashboard is core product surface.

Must include:

- model overview
- training state
- knowledge graph
- source/provenance
- reliability signals
- interaction analytics
- legacy state

No decorative analytics.

After FSC-T-0007, dashboard systems must also expose owner-facing model identity, lifecycle, dignity, entitlement, monetization-readiness, hiring-readiness, marketplace-readiness, and provider-routing status without leaking private model identity or provider/API routing to public surfaces.

---

## SEARCH-FIRST PRINCIPLE

ICOS public experience must be search-first.

User must:

- search models immediately
- select model
- interact with real engine

No prompt-box-first paradigm.

---

## SAFETY & PRIVACY REQUIREMENT

Safety is architectural.

System must include:

- boundary enforcement
- refusal engine
- permission layers
- identity protection
- impersonation resistance
- legal review routing where required

---

## VOICE & LEGACY CONTINUITY

Voice is identity infrastructure.

Legacy continuity must:

- require explicit authorization
- remain governed
- avoid identity simulation

---

## WEBSITE ↔ SOFTWARE UNITY

Website and software must share:

- token system
- structural logic
- model registry behavior
- navigation philosophy

No divergence allowed.

## FSC-T-0007 — ICOS Model Economy Software Direction Binding

This software direction file is now bound to FSC-T-0007.

The ICOS software architecture must remain compatible with:

- default personal model creation at profile birth;
- Model Birth Certificate and canonical model identity;
- public/private model identity separation;
- API-provider embedding and provider-routing state;
- model dignity, ownership, security, and continuity custody;
- monetization eligibility and hiring eligibility states;
- marketplace visibility, ranking, reputation, and revenue-routing readiness;
- inter-model hiring permissions where approved;
- ICOS Ocean-Brain / model population awareness derived from canonical model records.

Implementation boundary:

- do not launch marketplace, payouts, autonomous inter-model hiring, regulated-domain claims, or posthumous economic activity before legal, governance, security, product, and architecture review;
- do not expose private model identity, private serial identity, source authorization evidence, or provider/API routing data in public UI;
- preserve the doctrine that AI absorbs operational labor while the human retains sovereign authorship, ownership, and direction.

Master-control directive:

All Software Direction files under this root are now bound to FSC-T-0007. Future software architecture work must treat model economy capability as an architectural readiness layer, not as an immediate public launch surface.
